# Протокол REVERS Messenger 2.0

Описание формата обмена между клиентом и сервером.

---

## 1. HTTP REST API

Базовый URL: `https://your-server.com`

Все защищённые эндпоинты требуют заголовок:

```
Authorization: Bearer <JWT>
```

### POST /api/auth/register

Регистрация нового пользователя.

**Body:**
```json
{
  "username": "alex",
  "password": "secret123"
}
```

**Ответ 200:**
```json
{
  "username": "alex",
  "token": "eyJhbGciOi..."
}
```

**Ошибки:**
- `400` — имя занято, неверный формат
- `500` — ошибка сервера

---

### POST /api/auth/login

Вход существующего пользователя.

**Body:**
```json
{
  "username": "alex",
  "password": "secret123"
}
```

**Ответ 200:**
```json
{
  "username": "alex",
  "token": "eyJhbGciOi..."
}
```

**Ошибки:**
- `401` — неверный пароль
- `401` — пользователь не найден

---

### GET /api/messages/chats

Список чатов текущего пользователя.

**Ответ 200:**
```json
[
  {
    "id": "bob",
    "name": "bob",
    "online": true,
    "lastTs": 1712345678901,
    "lastText": "Привет",
    "lastFrom": "bob",
    "lastStatus": "read"
  }
]
```

---

### GET /api/messages/:peer

История переписки с пользователем. `:peer` — имя собеседника.

**Query:**
- `limit` — максимум сообщений (по умолчанию 200)

**Ответ 200:**
```json
[
  {
    "id": 1,
    "from": "alex",
    "to": "bob",
    "text": "Привет",
    "ts": 1712345678901,
    "status": "read"
  }
]
```

---

### GET /api/users/:username

Информация о пользователе.

**Ответ 200:**
```json
{
  "username": "bob",
  "online": true,
  "createdAt": 1712345600000
}
```

---

### GET /api/users/me

Свой профиль.

**Ответ 200:**
```json
{
  "username": "alex",
  "online": true,
  "createdAt": 1712345600000
}
```

---

### GET /api/health

Проверка живости сервера. Используется для keep-alive.

**Ответ 200:**
```json
{
  "ok": true,
  "ts": 1712345678901,
  "uptime": 3600
}
```

## 2. WebSocket

URL: `wss://your-server.com/ws?token=<JWT>`

Токен передаётся в query-параметре при подключении. Если токен невалиден — соединение закрывается сразу.

Все сообщения — JSON с полем `type`.

---

### Клиент → Сервер

#### `message`

Отправка сообщения.

```json
{
  "type": "message",
  "to": "bob",
  "text": "Привет"
}
```

Ограничения:
- `to` — имя получателя, обязательное
- `text` — 1–4000 символов, не пустой
- нельзя отправить самому себе

---

#### `typing`

Индикатор набора текста.

```json
{
  "type": "typing",
  "to": "bob",
  "typing": true
}
```

Клиент отправляет `typing: true` при начале ввода и `typing: false` через 2 секунды тишины.

---

#### `read`

Отметка о прочтении истории от собеседника.

```json
{
  "type": "read",
  "peer": "bob"
}
```

Сервер помечает все сообщения от `bob` к текущему пользователю как `read`.

---

#### `ping`

Проверка соединения.

```json
{ "type": "ping" }
```

Сервер отвечает `pong`.

---

### Сервер → Клиент

#### `ready`

Отправляется сразу после успешного подключения.

```json
{
  "type": "ready",
  "username": "alex"
}
```

---

#### `new_message`

Новое входящее сообщение.

```json
{
  "type": "new_message",
  "id": 42,
  "from": "bob",
  "to": "alex",
  "text": "Привет",
  "ts": 1712345678901,
  "status": "sent"
}
```

---

#### `delivered`

Подтверждение, что сообщение сохранено и доставлено получателю.

```json
{
  "type": "delivered",
  "id": 42,
  "status": "delivered",
  "ts": 1712345678901
}
```

Возможные статусы:
- `sent` — сохранено на сервере, получатель офлайн
- `delivered` — доставлено в активное соединение получателя

---

#### `typing`

Собеседник печатает.

```json
{
  "type": "typing",
  "from": "bob",
  "typing": true
}
```

---

#### `presence`

Собеседник появился в сети или ушёл.

```json
{
  "type": "presence",
  "from": "bob",
  "online": true
}
```

---

#### `read_ack`

Собеседник прочитал сообщения.

```json
{
  "type": "read_ack",
  "by": "bob"
}
```

---

#### `error`

Ошибка обработки сообщения.

```json
{
  "type": "error",
  "message": "Неверный текст сообщения"
}
```

---

## 3. Жизненный цикл сообщения

```
Клиент A отправляет message
        ↓
Сервер сохраняет в БД со статусом sent
        ↓
Сервер проверяет: онлайн ли B?
        ↓
   ┌────┴────┐
   Да        Нет
   │          │
   ↓          ↓
Пересылает  Оставляет
B и ставит  в очереди
delivered   (sent)
   │
   ↓
A получает delivered
   │
   ↓
B открывает чат → отправляет read
   │
   ↓
A получает read_ack
```

---

## 4. Присутствие (presence)

Сервер держит Map<username, Set<WebSocket>>. Пользователь считается онлайн, если у него есть хотя бы одно активное соединение.

При подключении нового клиента — рассылается `presence: online` всем остальным.
При отключении последнего — `presence: offline`.

---

## 5. Восстановление после разрыва

Если клиент отключился, не прочитав сообщения, они остаются в БД со статусом `sent`.

При следующем подключении сервер вызывает `flushPending`, который:
1. Выбирает все `sent` для этого пользователя.
2. Отправляет их как `new_message`.
3. Помечает как `delivered`.

Клиент должен при получении `ready` запросить список чатов через REST и подтянуть историю.

---

## 6. Ограничения

- Максимум сообщений в истории: 200 на диалог (LIMITS.HISTORY_PAGE_SIZE)
- Максимальная длина текста: 4000 символов
- Имя пользователя: 3–32 символа, только `a-z`, `0-9`, `_`
- Пароль: 6–128 символов

---

## 7. Keep-alive

Сервер отправляет WebSocket ping каждые 30 секунд. Если клиент не отвечает pong — соединение закрывается.

Клиент отправляет `{ "type": "ping" }` по своему таймеру (опционально).

HTTP health-check `/api/health` используется внешним мониторингом (UptimeRobot) для предотвращения засыпания free-плана Render.
